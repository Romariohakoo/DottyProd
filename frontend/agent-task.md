# Расширение карты поездки: хронология, активное событие и добавление места

## Цель

Доработать существующий дашборд поездки:

1. Соединить соседние по времени события аккуратными изогнутыми контрастными стрелками.
2. Синхронизировать выбор события на карте, в таймлайне и инспекторе через query-параметр `active-event-id`, с восстановлением после обновления страницы.
3. Реализовать добавление места кликом по карте или организации Яндекса с предзаполнением привычной формы и переключателем видимости организаций и транспорта.

Работать по `AGENTS.md`, по аналогии с существующим кодом. Этот файл описывает будущую реализацию. Подготовка задания сама по себе не является разрешением менять код или запускать агентов.

## Текущая реализация и аналоги

Перед началом перепроверить актуальные файлы и `git status`: состояние могло измениться после подготовки задания. Существующие пользовательские изменения сохранять.

- `src/widgets/trip-map/ui/TripMap.tsx`: получает места и события; строит только прямые линии для `movement`, с разным пунктиром по транспорту.
- `src/entities/place/ui/place-map.tsx`: общий рендер карты, маркеров и линий через Yandex Maps v3 / Reactify. Маркеры сейчас не выбирают события. Customization скрывает POI, transit и большую часть подписей.
- `src/entities/event/ui/event-day-timeline.tsx`: существующие `selectedId` и `onSelect`.
- `src/widgets/event-inspector/ui/EventInspector.tsx`: отображение выбранного события, закрытие и редактирование.
- `src/features/place/create/ui/CreatePlaceForm.tsx`: стандартная форма, `react-hook-form`, схема, mutation и callback успешного создания.
- `src/features/place/update/ui/UpdatePlaceForm.tsx`: аналог заполнения формы существующими значениями.
- `src/entities/place/ui/place-address-search.tsx`: существующие поиск адреса, состояния загрузки и ошибки, установка адреса и координат.
- `src/entities/place/api/geocode-address.ts`: существующий HTTP Geocoder. Сейчас принимает `uri`, а не произвольные координаты; нельзя считать обратное геокодирование готовым.

Данные брать из существующего detail/cache поездки. Не добавлять отдельные GET-запросы событий или мест. Использовать актуальные `Event`, `Place`, типы SDK и значения формы; не менять доменные типы, DTO, схемы и API-контракты.

## 1. Переходы между событиями

### Основное поведение

- Стрелки показывают временную последовательность событий текущего фильтра дня / «Все дни», а не только события типа `movement`.
- Порядок совпадает с таймлайном: время `startAt` по возрастанию, при равенстве — `id`. Не мутировать массив из query/cache.
- Каждая пара соседних событий с определёнными местами получает направленную связь от более раннего к более позднему. В «Все дни» учитывать переход через границу суток.
- Это визуальная связь событий. Построение автомобильных, пешеходных маршрутов по дорогам, расчёт расстояний и времени в задачу не входят.
- Сохранить отображение самого перемещения `fromPlace → toPlace` и смысл существующего оформления транспорта; согласовать его с новыми связями, исключив случайное двойное наложение.

### Внешний вид

- Плавная дуга с отчётливым наконечником в направлении следующего события.
- Контрастная основная линия с подложкой/обводкой, читаемая поверх улиц, воды и подписей; использовать существующие цвета/токены.
- Линия не перекрывает содержимое маркеров и не перехватывает клики по карте, POI и маркерам.
- Стрелки корректно следуют за картой при pan/zoom/resize. Не использовать абсолютные экранные координаты без синхронизации с проекцией.
- Для 0–1 события связи отсутствуют; совпадающие координаты не создают вырожденную дугу, `NaN` или огромную петлю.

### Уточнения перед реализацией

Если проект не задаёт эти правила, вынести на согласование вместе с техническим планом. Предлагаемые варианты по умолчанию:

- Для activity использовать `place`; для связи между событиями выход из movement — `toPlace`, вход в movement — `fromPlace`.
- Если у промежуточного события нет места, не проводить связь «через него», создавая впечатление, что события непосредственно соседние.
- При совпадении мест соседних событий не рисовать нулевую стрелку; события остаются доступны для выбора.

## 2. Единый выбор через `active-event-id`

- URL — источник истины выбранного события. Заменить независимый локальный `focusedId`, не поддерживать второй несинхронизированный выбор.
- Выбор из карты и таймлайна обновляет `active-event-id`; инспектор, подсветка события и связанного места используют одно и то же событие.
- Закрытие инспектора удаляет только `active-event-id`. Удаление активного события также очищает выбор; удаление другого события не сбрасывает его.
- Обновление страницы и переходы браузера назад/вперёд восстанавливают выбор из URL.
- Сохранять `opened-tab`, `open-popup-type`, `open-popup-id` и остальные query-параметры. Обновлять URL по существующему образцу, без полной перезагрузки и скачков прокрутки.
- Проверять ID: отсутствующий, пустой, нечисловой, дробный, неположительный или отсутствующий в загруженной поездке ID не должен ломать интерфейс. Не объявлять ID отсутствующим до окончания загрузки данных.
- Выбор события не равен открытию окна редактирования: не подменять его `open-popup-id`.
- При смене дня не сбрасывать активный ID молча. На прямой ссылке/после reload выбранное событие должно оставаться доступным в отображаемом таймлайне и на карте; предложить и согласовать минимальное правило согласования с текущим фильтром дня.
- Сохранить обычное открытие деталей/редактирования из списка событий; если список тоже обновляет активный ID, делать оба изменения URL одной операцией.

### Неоднозначность маркеров

Сейчас карта показывает места, а одно место может принадлежать нескольким событиям. До реализации согласовать UX: отдельные маркеры событий либо выбор события из компактного списка у общего маркера. Рекомендация — сохранить существующие маркеры мест, при одном событии выбирать его сразу, при нескольких показывать доступный список в хронологическом порядке.

Нельзя молча выбирать первое событие по месту. Учесть оба конца movement, повторные посещения одного места, совпадение координат разных мест и места без событий. Место без событий не получает вымышленный `active-event-id`. Не менять смысл существующей нумерации мест.

## 3. Добавление места с карты

### Режим выбора

- В левом верхнем углу карты кнопка «Поставить точку» включает режим выбора позиции.
- В режиме выбора текст — «Отменить добавление». Повторный клик отменяет режим без открытия формы и без сохранения места.
- Показать понятную подсказку о выборе точки/организации и визуальный признак режима; предусмотреть отмену через Escape.
- Управление доступно только при наличии прав редактирования. Для viewer карта, просмотр POI и выбор события продолжают работать.
- Клики по кнопкам, переключателю, пользовательским маркерам и выбору события не должны случайно создавать место. Перетаскивание и zoom также не считаются выбором точки.
- Обычный клик по фону карты вне режима добавления не открывает форму.

### Выбор произвольной точки

- В режиме добавления клик по карте определяет координаты и запускает получение адреса.
- Открывать существующий popup `create-place` с заполненными координатами и найденным адресом. Название пользователь может ввести сам; не выдавать адрес за название организации.
- Координаты выбранной точки сохранять точно: в SDK порядок `[longitude, latitude]`, в форме — соответствующие поля. Геокодирование адреса не должно незаметно перемещать выбранную точку в центр ближайшего дома.
- Существующие валидация, mutation, обработка ошибок, закрытие по успеху и обновление cache сохраняются. Сам клик ничего не сохраняет в backend.

### Организации и транспорт

- Рядом с кнопкой добавления, в левом верхнем углу карты, разместить подписанный переключатель «Показывать организации и транспорт».
- По умолчанию выключен: сохранить текущую упрощённую карту. Во включённом состоянии отображать доступные в Яндексе POI, заведения, остановки, метро и их подписи с учётом масштаба/доступности слоя.
- Переключатель действует независимо от режима добавления и доступен также для просмотра. Не пересоздавать карту и не сбрасывать положение при переключении.
- Проверить весь текущий набор customization: простого удаления запрета `poi` недостаточно, если другие правила продолжают скрывать точки, иконки или подписи.
- В режиме добавления клик по POI открывает ту же форму с названием организации, её координатами и адресом. Использовать геометрию организации, а не координаты указателя рядом с подписью.
- Не считать, что все метаданные уже есть в событии клика SDK. Проверить реальные payload и поддерживаемый способ получения информации об организации/транспортном объекте.
- Один клик по POI не должен одновременно обрабатываться как клик по фону и открывать две формы/два запроса.

### Жизненный цикл и ошибки

- Предлагаемый сценарий: после успешного выбора точки/POI выйти из режима выбора и открыть форму; закрытие формы без сохранения очищает черновик, следующее обычное создание места открывается пустым.
- При загрузке адреса показывать статус. Отмена, повторный выбор, смена поездки или уход со страницы делают старый ответ неактуальным: он не открывает popup и не перезаписывает новый выбор/введённые поля.
- При ошибке/403/таймауте показывать понятное сообщение и возможность повторить выбор или отменить действие. Не выдавать ошибку API за отсутствие адреса.
- Если успешный ответ не содержит адреса либо части данных POI, объяснить, что не найдено; сохранить известные координаты и разрешить заполнить недостающее в существующей форме. Не подставлять вымышленные данные и не ослаблять схему.
- Начальные значения должны применяться при открытии новой формы и не перезаписывать пользовательский ввод на каждом рендере. Предзаполненное место должно создаваться без обязательного повторного поиска адреса.
- Режим добавления и черновик не требуется сохранять после reload; требование persistence относится к `active-event-id`.

## Стратегия мультиагентов

Использовать после разрешения на реализацию: ведущий интегратор и до трёх исполнителей. До этого агентов не запускать.

### Этап A: единый разбор и фиксация границ

Ведущий проверяет рабочее дерево, аналоги, документацию SDK и блокеры; получает необходимые решения пользователя. До параллельного редактирования фиксирует точный список файлов каждого исполнителя, имена и сигнатуры props/callbacks, формат предзаполнения, правила выборки событий и обработки кликов. Использовать существующие типы и допустимые локальные props; новый общий контракт требует согласования пользователя.

### Этап B: параллельная работа с исключительным владением файлами

| Исполнитель | Задача | Владение |
| --- | --- | --- |
| Агент 1 — хронология | Подготовка связей событий и данных выбора по утверждённым правилам | `src/widgets/trip-map/**`; новые внутренние файлы только в согласованном списке |
| Агент 2 — карта и SDK | Отрисовка дуг/наконечников, интерактивные маркеры, фон/POI clicks, слои организаций, получение адреса/POI в пределах согласованного доступа | `src/entities/place/ui/place-map.tsx`; необходимые файлы `src/entities/place/api/**` только после согласования |
| Агент 3 — форма | Предзаполнение существующей формы, корректная инициализация/очистка, сохранение текущего ручного сценария | `src/features/place/create/ui/CreatePlaceForm.tsx` |
| Ведущий | `active-event-id`, фильтр дня, режим добавления, toolbar, popup/черновик, интеграция callbacks и общая проверка | `src/pages/trips/ui/TripPage.tsx`; согласованные public `index.ts` и остальные интеграционные файлы |

- Все изменения `place-map.tsx`, включая стрелки и клики, делает только агент 2. Агент 1 передаёт данные через заранее согласованные props, не редактирует этот файл.
- `TripPage.tsx` меняет только ведущий. Агентам не поручать «самостоятельно подключить свою часть к странице».
- `EventInspector`, таймлайн, `PlaceAddressSearch`, shared SDK helper и public exports по умолчанию читать; если изменение необходимо, ведущий сначала согласует объём и назначает единственного владельца.
- Если инструменты работают в общем checkout, учитывать, что изменения сразу общие. Не использовать массовое форматирование, reset/restore/clean/stash и не переносить чужие файлы. Изоляция Git не возникает автоматически.
- Изолированные worktree использовать только по согласованному плану с абсолютными путями и способом переноса изменений; не смешивать эту схему с редактированием тех же файлов в общем checkout.
- Если нужен файл другого владельца, отправить запрос ведущему. Изменение общего интерфейса согласовать со всеми потребителями до правки. Не запускать дополнительных агентов на те же файлы.
- Каждый исполнитель сдаёт список изменённых файлов, использованные аналоги, выполненные проверки и ограничения. Не делать commit/push без отдельного запроса.

### Этап C: интеграция

Ведущий подключает результаты, проверяет FSD и все три сценария вместе. Если агент заблокирован SDK/контрактом, остальные продолжают независимые части в своих границах; блокер нельзя обходить выдуманными данными или заглушкой под видом готовой функциональности.

После завершения правок исполнителей ведущий единолично запускает общие проверки: `pnpm check` включает ESLint autofix, поэтому его нельзя запускать одновременно с чужим редактированием.

## Ограничения

- FSD: entities не импортируют Event из соседней entity или feature создания места. Композиция событий и мест — на существующем уровне widget/page; callbacks идут через props.
- Не вводить отдельный глобальный store или новый способ загрузки данных.
- Не менять API-контракты, типы предметной области, схемы, зависимости, lockfile, root layout, providers, middleware и конфиги без отдельного согласования.
- Общий `PlaceMap` используется также в поиске адреса: новые возможности должны быть опциональными, текущие потребители продолжают работать.
- Использовать существующий UI kit и токены; адаптивность, управление с клавиатуры, focus, доступные названия и состояния переключателя обязательны. Не требовать от пользователя только клика мышью: существующее ручное добавление места должно оставаться доступным.
- Не менять посторонние файлы и пользовательские изменения, в том числе `LoginForm.tsx`.

## Приёмка и проверка

После реализации выполнить `pnpm check` и `pnpm build`. Учитывать autofix в `check`, просмотреть итоговый diff; случайные изменения не включать. Если ошибка вне задачи, описать её отдельно. Тесты добавлять по существующим аналогам для нетривиальных правил, без новой тестовой инфраструктуры.

В браузере проверить:

1. Последовательность из нескольких activity и movement: связи всех соседних событий, направление наконечников, одинаковое время, разные дни, отсутствие места и совпадающие координаты.
2. Читаемость стрелок при zoom/pan/resize, в плотной городской карте и на мобильном экране.
3. Выбор события с карты и таймлайна: единый URL, инспектор и подсветка; несколько событий у одного места и место без событий.
4. Прямая ссылка с `active-event-id`, reload, назад/вперёд, некорректный ID, удалённое событие, смена дня и сохранение остальных query-параметров.
