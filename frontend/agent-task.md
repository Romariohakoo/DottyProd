# Задача: CRUD для TravelHub

Нужно реализовать CRUD-функциональность для `trip`, `place` и `event`. Работу с `attachment` пока не реализовывать.

## Источники правды и ограничения

- Соблюдай `AGENTS.md`.
- Бизнес-правила и семантика находятся в `agents/travelhub-data-api.md`.
- Эндпоинты, request body и response body находятся в `agents/openapi.json`.
- Если Markdown-спецификация и OpenAPI расходятся, не принимай решение самостоятельно: остановись, опиши конкретное расхождение и предложи варианты.
- Не придумывай отсутствующие backend-эндпоинты.
- Не добавляй зависимости и не меняй конфиги.
- Не реализовывай ничего, связанного с загрузкой, получением или удалением вложений.
- Поле `attachments`, которое может приходить в ответах событий, пока не типизируй, не преобразовывай и не отображай. Просто игнорируй его как неиспользуемое дополнительное поле ответа.
- `client_request_id` пока не нужен: не добавляй его в формы, application-модели и тела запросов.
- Дизайн должен быть максимально простым, читаемым и совместимым с существующим тёмным фоном. Используй существующие Tailwind-токены и UI-компоненты.
- Делай минимальные изменения без побочного рефакторинга.

В рамках этой задачи явно разрешено:

- создавать новые transport-типы и типы сущностей Trip, Place и Event строго по спецификации и OpenAPI;
- создать общий TravelHub transport-контракт в `shared/api`, чтобы entity-срезы не импортировали друг друга;
- вынести в `shared/api` общий query key/query options, необходимый для чтения `TripDetail` несколькими entity-срезами;
- изменить `src/shared/api/client.ts`, чтобы исходящие JSON-тела автоматически преобразовывались из `camelCase` в `snake_case` с помощью уже существующих `convertKeys` и `camelToSnake`;
- создать страницы `/trips` и `/trips/[tripId]` и необходимые компоненты композиции более высокого FSD-слоя.

Существующие типы, шаблоны компонентов и API-контракты не изменяй без отдельной необходимости, прямо вытекающей из этой задачи.

## Обязательный порядок работы

Сначала полностью спланируй работу и только после этого начинай писать код этапа 1.

До первого изменения кода:

1. Прочитай `AGENTS.md`, обе спецификации из `agents` и текущие аналоги.
2. Назови ближайшие аналоги, на которых будет основана реализация. Минимум проверь:
   - `src/entities/user`;
   - `src/features/user/register`;
   - `src/features/user/update-user`;
   - `src/shared/ui/dialog.tsx`;
   - `src/shared/api/client.ts`;
   - существующие страницы в `app`.
3. Представь план по этапам 1–4. Для каждого этапа перечисли предполагаемые файлы, зависимости, query keys, правила инвалидации кэша и способ интеграции UI со страницами.
4. Отдельно опиши, как Place и Event будут читаться из кэша `TripDetail` без дополнительных HTTP-запросов и без импортов между соседними entity-срезами.
5. Если после изучения проекта остаётся блокирующая неоднозначность, сначала задай вопрос. В противном случае после представления плана переходи к этапу 1.

Не начинай этапы 2–4, пока этап 1 не завершён и не проходит `pnpm check`. Аналогично не переходи к следующему этапу, пока текущий не завершён и не проверен.

## Архитектурные решения задачи

### Transport-типы и FSD

Положи общий transport-контракт TravelHub в `shared/api`. Он должен содержать только типы, которые реально нужны для Trip, Place и Event в этой задаче, и соответствовать OpenAPI с учётом того, что `attachments` и `client_request_id` сейчас намеренно не используются.

Entity-срезы `entities/trip`, `entities/place` и `entities/event` могут импортировать transport-типы только из публичного API `shared/api`. Импорты между этими entity-срезами запрещены.

Общие query keys/query options для `TripDetail`, необходимые нескольким entity-срезам, также размести в `shared/api`. Не дублируй строковые query keys в разных срезах.

### Преобразование регистра полей

В текущем API-клиенте ответы уже преобразуются из `snake_case` в `camelCase`, но исходящие request body пока не преобразуются. Добавь в request interceptor преобразование JSON-данных из `camelCase` в `snake_case` через существующие `convertKeys` и `camelToSnake`.

Требования к преобразованию:

- не преобразовывай `FormData`, `Blob`, бинарные данные и другие не-plain-object значения;
- не ломай установку Authorization-заголовка и refresh flow;
- не дублируй ручное преобразование внутри каждой API-функции;
- добавь проверку по аналогии с существующими тестами, если в проекте есть подходящий тестовый шаблон. Если аналога тестов нет, не вводи новый тестовый стек.

### Получение данных

Отдельные GET-запросы существуют только для Trip:

- `GET /api/trips` — список поездок;
- `GET /api/trips/{tripId}` — `TripDetail`.

Отдельных GET-эндпоинтов для Place и Event нет. Они читаются только из результата `GET /api/trips/{tripId}`:

- Place — массив `TripDetail.places`;
- Event — массив `TripDetail.timeline`.

Query-хуки Place и Event должны подписываться на тот же React Query cache entry `TripDetail` и получать данные через `select` либо эквивалентный реактивный механизм. Они не должны отправлять дополнительные запросы, если `TripDetail` уже находится в кэше, и не должны использовать непубличные импорты или импорты между entity-срезами.

На странице `/trips/[tripId]` значение `tripId` берётся из route params. `placeId` или `eventId` для выбранной сущности берётся из query-параметра `open-popup-id`.

На странице `/trips` ID выбранной поездки берётся из `open-popup-id`.

### Состояние попапов

Используй существующий `shared/ui/Dialog`.

Для попапов выбранной сущности используй:

```text
?open-popup-type=trip&open-popup-id=1
?open-popup-type=place&open-popup-id=2
?open-popup-type=event&open-popup-id=3
```

Для формы создания используй отдельное значение без ID:

```text
?open-popup-type=create-trip
?open-popup-type=create-place
?open-popup-type=create-event
```

При закрытии попапа удаляй только `open-popup-type` и `open-popup-id`, сохраняя остальные query-параметры. Не открывай одновременно более одного CRUD-попапа.

## Этап 1. Entities и чтение данных

Создай:

- `entities/trip`;
- `entities/place`;
- `entities/event`.

Структуру каждого среза делай по аналогии с `entities/user`: `api`, `model`, `ui` и публичные `index.ts`. Не добавляй сегменты и абстракции, которые не нужны задаче.

### Trip

Реализуй:

- типы Trip, TripCard и TripDetail на основе общего transport-контракта;
- API-функцию получения списка поездок;
- API-функцию получения `TripDetail` по `tripId`;
- query keys;
- `useTripsQuery`;
- `useTripQuery(tripId)`;
- простой компонент списка поездок, показывающий только `title`;
- простой компонент подробной информации о выбранной поездке со всеми используемыми полями.

Клик по элементу списка должен открыть попап выбранной поездки через query-параметры.

### Place

Реализуй:

- тип Place на основе общего transport-контракта;
- `usePlacesQuery(tripId)`, который читает `places` из кэша `TripDetail`;
- `usePlaceQuery(tripId, placeId)`, который находит место по ID в `TripDetail.places`;
- простой список мест, показывающий `name`, потому что у Place нет поля `title`;
- простой компонент подробной информации о выбранном месте со всеми используемыми полями.

Не создавай GET-запросы Place.

### Event

Реализуй:

- discriminated union для `activity` и `movement` на основе общего transport-контракта;
- `useEventsQuery(tripId)`, который читает `timeline` из кэша `TripDetail`;
- `useEventQuery(tripId, eventId)`, который находит событие по ID в `TripDetail.timeline`;
- простой список событий, показывающий `title`;
- простой компонент подробной информации с корректным набором полей для `activity` и `movement`.

Не создавай GET-запросы Event и не обрабатывай `attachments`.

После создания простых компонентов подключи их к страницам, описанным ниже. Сначала компонент должен быть готов принимать данные через props, и только после этого его можно интегрировать в страницу.

## Этап 2. Создание сущностей

Создай:

- `features/trip/create`;
- `features/place/create`;
- `features/event/create`.

Каждая feature должна повторять структуру существующих form-features: `api`, `model`, `ui` и публичные `index.ts`.

Для каждой сущности реализуй:

- request DTO по OpenAPI без `client_request_id`;
- API-функцию;
- Zod-валидацию по ограничениям OpenAPI и Markdown-спецификации;
- React Query mutation hook;
- простую форму со всеми необходимыми полями;
- pending и error states;
- корректную инвалидацию кэша после успеха.

Сначала создай самостоятельный компонент формы, принимающий необходимые props. После этого открой его в create-попапе соответствующей страницы.

Event-форма должна поддерживать оба варианта события:

- `activity`: `type`, `title`, `description`, `startAt`, `endAt`, `bookingUrl`, `category`, необязательное `place`;
- `movement`: `type`, `title`, `description`, `startAt`, `endAt`, `bookingUrl`, `transportType`, `fromPlace`, `toPlace`.

Для `place`, `fromPlace` и `toPlace` пользователь должен иметь возможность:

- выбрать существующее место поездки и отправить `PlaceRef`;
- выбрать создание нового места и заполнить `PlaceInput`.

Переключение `activity`/`movement` должно очищать неактуальные поля, чтобы запрос соответствовал discriminated union из OpenAPI.

После успешного создания:

- инвалидируй список поездок или `TripDetail` в зависимости от сущности;
- закрой попап;
- при ошибке оставь попап открытым и покажи понятное сообщение.

## Этап 3. Удаление сущностей

Создай:

- `features/trip/delete`;
- `features/place/delete`;
- `features/event/delete`.

Для каждой сущности реализуй API-функцию, mutation hook и кнопку удаления.

Кнопка удаления находится внутри попапа выбранной сущности. Подтверждение сделай простым двухшаговым состоянием внутри того же попапа: первое нажатие показывает предупреждение и кнопки подтверждения/отмены, второе подтверждённое действие отправляет запрос.

Не используй `window.confirm`, если в проекте нет такого аналога.

После успешного удаления:

- инвалидируй соответствующие query keys;
- закрой попап;
- для удаления Trip верни пользователя на `/trips`, если удаление произошло со страницы конкретной поездки;
- при ошибке оставь попап открытым и покажи сообщение;
- для `409 PlaceInUse` выведи отдельное понятное сообщение о том, что место используется событием.

## Этап 4. Редактирование сущностей

Создай:

- `features/trip/update`;
- `features/place/update`;
- `features/event/update`.

Все update-эндпоинты имеют PUT-семантику, а не PATCH-семантику.

Для каждой сущности:

- форма инициализируется текущими значениями;
- в запрос отправляется полное состояние всех изменяемых полей, даже если пользователь поменял только одно поле;
- пропущенные необязательные поля должны явно соответствовать ожидаемому OpenAPI-значению;
- неизменяемые данные показываются текстом;
- кнопка сохранения доступна только при валидной форме и наличии изменений;
- после успешного PUT инвалидируется нужный кэш и попап закрывается;
- при ошибке попап остаётся открытым.

Для Event:

- `type` менять нельзя;
- существующий `type` показывается текстом и передаётся в PUT body;
- набор редактируемых полей зависит от `activity` или `movement`;
- выбор существующего или нового места должен работать так же, как в create-форме.

На этом этапе замени простое отображение деталей в попапе на update-форму. Неизменяемые поля оставь в виде текста. Кнопка удаления из этапа 3 остаётся в этом же попапе.

## UI и интеграция со страницами

### `/trips`

Страница содержит:

- список всех поездок;
- кнопку открытия create-trip попапа;
- попап выбранной поездки по `open-popup-id`;
- на этапах 3–4 — удаление и редактирование выбранной поездки внутри этого попапа;
- loading, empty и error states.

На этапе 1 попап только показывает подробные данные. На этапе 4 отображение изменяемых полей заменяется update-формой.

### `/trips/[tripId]`

Сделай небольшой dashboard:

- слева вертикальные вкладки `Общее`, `Места`, `События`;
- справа содержимое активной вкладки;
- активная вкладка хранится в локальном состоянии страницы, по умолчанию открыто `Общее`;
- `Общее` пока показывает только `title` поездки;
- `Места` показывает список мест и кнопку создания места;
- `События` показывает список событий и кнопку создания события;
- клик по месту или событию открывает соответствующий попап через `open-popup-type` и `open-popup-id`;
- на этапах 3–4 удаление и редактирование находятся внутри попапа выбранной сущности;
- для всех секций реализуй loading, empty и error states.

Страница отвечает за композицию entity и feature-компонентов. Не помещай page-specific orchestration в entity или feature.

## Мультиагентная работа

Этап 1 выполняет главный агент без субагентов, потому что на нём создаются общие transport-типы, query keys и зависимости между слоями.

На этапах 2–4 обязательно используй три субагента параллельно:

- один для Trip;
- один для Place;
- один для Event.

Перед запуском субагентов главный агент:

1. Определяет точные границы файлов для каждого субагента.
2. Создаёт или фиксирует общие публичные контракты, которые понадобятся всем троим.
3. Запрещает субагентам одновременно редактировать shared-код, страницы композиции и одни и те же barrel-файлы.

Субагенты работают только в своих entity-specific feature-папках. Главный агент после их завершения:

- проверяет соответствие общим типам и FSD-правилам;
- объединяет результаты;
- обновляет публичные API там, где это нельзя было безопасно делать параллельно;
- интегрирует готовые компоненты в страницы;
- запускает итоговые проверки.

## Проверка и отчёт

После каждого этапа:

1. Запусти `pnpm check`.
2. Исправь ошибки, относящиеся к текущему этапу.
3. Если ошибка внешняя или требует изменения контракта, остановись и опиши её, не подавляя типизацию.
4. Проверь diff на отсутствие побочных изменений.
5. Кратко отчитайся:
   - что реализовано;
   - какой аналог использован;
   - какие файлы изменены;
   - что отличается от аналога и почему;
   - результат `pnpm check`;
   - что остаётся на следующем этапе.

Не используй `any`, `as unknown as`, `@ts-ignore`, `@ts-expect-error`, отключение lint-правил или ослабление типов. Не коммить и не отправляй изменения без отдельного запроса.
