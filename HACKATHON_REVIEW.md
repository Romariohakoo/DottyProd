## Дополнительно исправлено при согласовании

- Форма билета скрывала сбой загрузки фото через `.catch(() => undefined)`. Теперь ошибка видна, поездка перечитывается после попытки, повтор с теми же данными повторно использует событие и ключ фото.
- Повтор в галерее раньше создавал новый UUID при каждом вызове API. Ключ перенесён на уровень mutation и сохраняется до успеха с учётом поездки, события и файла.
- CI больше не затирает токен из `BACKEND_ENV` пустой CI variable и не включает уведомления принудительно. Непустой отдельный токен может переопределить исходный; флаг уведомлений остаётся в `BACKEND_ENV`.
- `FRONTEND_ENV` одинаково нормализуется при сборке и деплое для File variable, текста и отсутствующего значения. Отсутствие создаёт пустой файл, исключая настройки прошлого релиза.
- Исправлена группировка shell-условия создания `grafana.env`: ошибка предыдущей команды не должна превращаться в продолжение релиза через ветку `||`.
- Для единого Compose явно заданы внутренние порты PostgreSQL 5432 и backend 1984; значение по умолчанию backend 8080 больше не расходится с nginx и healthcheck.

### Дополнительные ошибки до демонстрации

1. **Повтор запроса может создать дубликат.** Backend поддерживает `client_request_id`, но frontend его не передаёт. Блокировка кнопки не защищает от повторной отправки после сетевого сбоя. Нужен стабильный идентификатор операции, сохраняющийся при повторе. См. [контракты frontend](frontend/src/shared/api/travelhub.dto.ts) и [TripService](backend/src/services/trip_service.py).
2. **Сокращение дат поездки через API может оставить события за её пределами.** Frontend проверяет это, а `TripService.update_trip()` — нет. Проверку следует выполнять на backend, внутри согласованной транзакции. См. [сервис](backend/src/services/trip_service.py) и [форму изменения поездки](frontend/src/features/trip/update/ui/UpdateTripForm.tsx).
3. **Кеш поездок не очищается при выходе.** Детали используют `staleTime: Infinity`, logout сбрасывает только текущего пользователя. При смене аккаунта в той же вкладке возможно отображение данных предыдущего пользователя из кеша. Нужно очищать приватные запросы при смене сессии. См. [кеш деталей](frontend/src/shared/api/trip-detail.query.ts), [logout](frontend/src/features/user/logout/model/use-logout-mutation.ts), [провайдер](frontend/src/app/providers/query-provider.tsx).

### Подробности ошибки времени

Frontend использует `new Date(values.startAt).toISOString()` и отправляет UTC. Backend проверяет `moment.date()` без преобразования в согласованный календарный часовой пояс поездки.

Пример: поездка начинается 4 ноября; пользователь в Москве задаёт событие на 4 ноября, 01:00. В запрос уходит `2026-11-03T22:00:00.000Z`. Backend сравнивает дату 3 ноября с началом поездки и отклоняет событие.

См. [создание события](frontend/src/features/event/create/ui/CreateEventForm.tsx) и `_validate_event_dates()` в [TripService](backend/src/services/trip_service.py).

### Подробности миграций

В рабочем дереве обнаружены две вершины:

- `fe62a8931c4d`;
- `b3c86f921a45`.

Причина — незакоммиченный файл [b3c86f921a45_remove_telegram_browser_binding.py](backend/migrations/versions/b3c86f921a45_remove_telegram_browser_binding.py), ответвляющийся от `a2b75e810f34`.

**В закоммиченном дереве вершина одна — `fe62a8931c4d`.** Нельзя переносить вывод о двух вершинах на текущий production или уже выполненный pipeline. Но запуск текущей рабочей копии через `alembic upgrade head` будет неоднозначным, и простое включение этого файла в следующий коммит перенесёт проблему в CI/деплой.

## 3. Оценка архитектуры

**Основа подходит для хакатона:** Next.js → FastAPI → PostgreSQL и S3. Слоистый монолит позволяет быстро развивать связанные сценарии и относительно просто разворачивается. Необходимости переходить на микросервисы по результатам аудита нет.

### Сильные стороны

- На backend разделены маршруты, сервисы, репозитории и схемы.
- Права доступа проверяются на сервере. Вложения выдаются после проверки доступа к поездке.
- Составные внешние ключи защищают связи событий с местами своей поездки.
- Есть транзакции, блокировки поездки, ограничения целостности и индексы.
- Связанные данные загружаются через `selectinload`.
- Изображения проверяются по содержимому; ограничены размер, число пикселей и количество вложений; создаются миниатюры.
- Frontend использует FSD, React Query, общие компоненты и проверки границ импортов.
- В backend есть содержательные интеграционные тесты с PostgreSQL и имитацией S3 через Moto.

### Что улучшить

1. **Синхронизация API-контрактов.** Типы frontend отстают от backend: например, нет `attachments` в событии и `client_request_id` во входных типах. Нужна проверяемая синхронизация с OpenAPI.
2. **Единая модель времени.** Сейчас проверки frontend и backend используют разные представления календарной даты. Это уже вызывает ошибку на границе поездки.
3. **Ответственности `TripService`.** Он объединяет доступ, CRUD, расписание, обработку изображений и файловое хранилище. Для хакатона допустимо; при развитии первым стоит выделить обработку вложений.
4. **Надёжная очистка S3.** После удаления записей ошибки удаления файлов только логируются. Нужна очередь повторной очистки или периодическое удаление объектов без записей в БД.
5. **Telegram relay.** Значение по умолчанию — HTTP-сервис; токен бота передаётся в URL запроса через него. Использовать HTTPS либо прямой Telegram API и явно задавать интеграцию окружением. См. [конфигурацию](backend/src/core/config.py) и [доставку уведомлений](backend/src/services/telegram_notifications.py).
6. **Приватный кеш frontend.** Очищать его при завершении и смене пользовательской сессии.

## 4. Оценка CI/CD

**Автоматизация существует, но готовность к надёжному релизу неполная.** Успешный pipeline сам по себе сейчас не доказывает готовность всего приложения к работе.

Основные файлы: [GitLab CI](.gitlab-ci.yml), [production compose](deploy/docker-compose.yaml), [backend Dockerfile](backend/Dockerfile), [frontend Dockerfile](frontend/Dockerfile), [nginx](deploy/nginx.conf), [Caddy](deploy/Caddyfile).

### Что сделано хорошо

- Backend-тесты запускаются с PostgreSQL, сохраняется JUnit-отчёт.
- Собираются отдельные образы backend и frontend, теги связаны с коммитом.
- Настроен автоматический деплой ветки `main`.
- Есть постоянные volumes для PostgreSQL, мониторинга и сертификатов.
- HTTPS обслуживает Caddy.
- Приложения запускаются в контейнерах от непривилегированных пользователей.
- PostgreSQL имеет healthcheck.

### Что исправить

| Проблема | Последствие | Доработка |
|---|---|---|
| Две вершины миграций в рабочей копии | `alembic upgrade head` неоднозначен, а команда выполняется перед стартом backend. | Разрешить ветвление. В закоммиченном дереве проблема не обнаружена. |
| Нет readiness backend/frontend и проверки после деплоя | Pipeline может закончиться успешно при неработающем приложении. | Healthchecks, ожидание готовности, проверки HTTPS/API и ключевого сценария. `/api/ping` не проверяет доступность БД и S3. |
| Нет описанного отката и восстановления БД | Возврат старого образа может не помочь после изменения схемы. | Хранить предыдущие версии; описать совместимость миграций, резервное копирование и проверенное восстановление. |
| Нет `resource_group` production | Два pipeline могут одновременно менять одну VM. | Сериализовать деплой. |
| Несогласованные порты | Backend по умолчанию слушает 8080, nginx и Prometheus ожидают 1984. | Зафиксировать единый порт либо явно задать `SERVER_PORT` в compose. Текущий production может получать верное значение из внешнего env-файла. |
| Конфигурация карт не воспроизводится явно | `NEXT_PUBLIC_*` нужны при сборке, но Dockerfile и CI не передают ключи карт явно. | Передавать публичную конфигурацию при сборке. Текущую работу карт в браузере проверить отдельно. |
| Frontend `checker` — независимая стадия Dockerfile | Её выполнение зависит от сборщика и настроек. | Отдельный обязательный CI job для types/lint, от которого зависит сборка. |
| `pnpm check` запускает `lint:fix` | Проверка может исправить файлы только внутри checker, а builder получает другую копию исходников. | В CI использовать lint без изменения файлов. |
| Ошибка сборки с `MANIFEST_FOR_TAG_EXISTS` превращается в успех | Возможно маскирование причины сбоя. | Отдельно проверять наличие ожидаемого образа; остальные ошибки оставлять ошибками. |
| Отключена проверка SSH-хоста | Не проверяется подлинность сервера. | Закрепить доверенный host key. |
| Telegram принудительно включается при деплое | Основной релиз зависит от дополнительной интеграции и наличия токена. | Управлять включением через окружение, сохраняя возможность запуска основного продукта отдельно. |

**Уточнение о checker:** нельзя утверждать, что текущий Kaniko обязательно пропускает эту стадию. Оригинальный Kaniko по умолчанию строит и неиспользуемые стадии; поведение зависит от реализации и флагов. Поэтому это риск зависимости проверки от сборщика, а не доказательство пропуска проверки в текущем pipeline. Источник: [документация Kaniko](https://github.com/GoogleContainerTools/kaniko#flag---skip-unused-stages).

Также frontend README утверждает, что `pnpm check` включает build, но фактический скрипт выполняет typecheck и lint с исправлениями. Документацию и реальные команды нужно согласовать.
